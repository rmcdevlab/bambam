# CR-061 — Local development through the production API

Status: DONE (approved and accepted 2026-11-26)
Requested: 2026-11-26 by owner
Size: M

## What changes

The owner defines `is_aok=true` as using the production API instead of connecting the local application directly to PostgreSQL. `is_aok=false` retains the existing database-backed runtime.

Approved scope: read-only access. The owner delegated scope and implementation choices with "ตามที่เหมาะสมได้เลย" on 2026-11-26, including the necessary Codex backend/shared-runtime/docs exception. Production writes require a separate explicit scope decision.

- Local browser -> local Next.js server -> HTTPS production API -> production PostgreSQL.
- Local server holds `secret_key` in ignored environment configuration. Never expose it through browser code, public environment variables, URLs or logs.
- Production validates a dedicated, revocable credential associated with an explicitly configured existing user. Existing service permissions and record visibility continue to apply; possession of a key does not grant Superadmin access or arbitrary impersonation.
- Support an explicit allowlist of read endpoints, including `/api/v1/me` and approved repair/settings reads and photo retrieval. Reject writes and auth/dev/internal routes for this credential. Review GET handlers for side effects before inclusion.
- Local API mode needs no `DATABASE_URL`; initialization, demo-user seeding, local SSO/session database operations and maintenance must not access PostgreSQL. Reject incompatible configuration and never fall back to a database when upstream requests fail.
- Provide local UI access for this server-configured principal without a local database session. Keep the normal production SSO login path and permissions intact. The API-mode local server must be bound to loopback; remote binding is outside this scope.
- Proxy only configured production paths. Use timeouts, disable redirects, preserve response/error envelopes and binary photos, and do not forward arbitrary browser authorization, cookie or upstream-selection headers.
- Document provisioning, local startup, rotation/revocation and return to database mode. Deliver the credential through private configuration; do not print its value in reports.

## Why

Allow local UI development using existing production data without distributing production database credentials or running database jobs from developer machines.

- Provisioning an existing user for the key requires owner selection; do not invent an identity or assign a role automatically.
- Existing production release and deployment procedures apply after implementation and verification.
